# Tech Blog Agent Instructions (포스팅 파이프라인 지침)

이 작업 영역(Workspace)은 티스토리 블로그 포스팅 최적화 파이프라인을 포함하고 있습니다. 모든 에이전트는 아래 규칙을 엄격히 준수합니다.

---

## 📂 1. 프로젝트 폴더 구조
- `drafts/{YYMMDD}_{Index}/`: 원천 소스 작업실 (`index.md` 초안, `thumbnail.jpg`, 로컬 이미지)
  - *폴더 자동 생성 규칙*: 당일 날짜(YYMMDD) 기준 기존 폴더 번호 다음 순번으로 자동 폴더 생성 (예: `260619_04/`)
- `dist/`: 컴파일 빌드 산출물 보관소 (로컬용, **Git 추적 배제**)
  - `dist/complete/`: 이미 발행이 완료된 과거의 빌드 폴더들을 모아서 아카이브하는 보관실.
  - **새 포스팅 지시 수임 시 청소 규칙 (필수)**: 사용자가 새로운 포스팅 작성 미션을 내리는 즉시, 이전에 `dist/` 루트에 빌드되어 쌓여있던 모든 과거의 날짜 형식 폴더들은 전부 `dist/complete/` 하위로 즉시 이동시켜 `dist/` 루트를 청소해야 합니다.
- `src/`: 빌드 엔진 및 CSS 템플릿 (`build.js`, `template.html`)

## ✍️ 2. 포스팅 초안 작성 및 완결형 딥다이브 규격 (Next-Level Standard)
- **타깃 독자**: 현업 AI/ML 연구원, 로보틱스/소프트웨어 엔지니어. (단순 뉴스 요약을 넘어 실무 적용 가치를 제공하는 최고급 기술 블로그 지향)
- **권장 분량**: 공백 포함 **3,500 ~ 5,000자 내외의 고밀도 완결형 딥다이브** (뉴스레터식 1~2천 자 단문 요약 금지).
- **어조 및 문체 믹스 (Tone Guide)**:
  - 하십시오체(50%, 사실/수치/구조) + 해요/죠체(30%, 주의환기/질문/해설) + 평서형/명사종결(20%, 빠른 요약/불릿).
  - Hype 단어(처참한, 압도적, 혁신적) 전면 배제하고 수치가 직접 말하게 할 것.
  - 전문 용어 영문 괄호 병기는 글 전체에서 **최초 1회만 허용**. 자명한 용어((Query), (Inference))는 괄호 삭제.

### 2-1. 필수 5단계 골든 포스팅 구조 (Standard 5-Stage Architecture)
모든 테크 블로그 포스팅은 반드시 다음 5단계 흐름을 따라 작성되어야 합니다:

1. **[1. Hook & Problem Context]**:
   - 시작부터 거창한 서론 대신, 가장 충격적인 비교 수치(예: $0.00070 vs $0.040, 79.08 vs 42.68)를 선제 제시.
   - 현업 엔지니어가 겪는 고질적 페인포인트(KV 캐시 메모리 폭증, 비디오 시점 통합 실패)와 연결.
2. **[2. Deep Architecture & Math Mechanics]**:
   - 단순 텍스트 서술을 넘어, 논문의 핵심 수식(`St = U(St-1, Dt)`, 좌표 변환식)이나 아키텍처 다이어그램(Figure 1)을 배치하고 작동 원리를 직관적으로 분해 설명.
3. **[3. Benchmark & Failure Breakpoint Analysis]**:
   - 총점만 나열하지 말고, **"모델이 어디서 어떻게 무너졌는가(Failure Cases & Breakpoints)"**를 정량 비교표(Table)로 심층 분석.
   - 정렬/중첩/복합 연산의 구조적 한계선(예: 8개 정렬 시 치수 붕괴, 상용 vs 오픈소스 병목 차이)을 면밀히 규명.
4. **[4. Implementation, System Discussion & Engineering Analysis]**:
   - 논문에서 실제로 다룬 프로덕션 구현체, 아키텍처 한계 및 트레이드오프, 벤치마크/비용 분석.
   - **논문 외 가공 콘텐츠 금지 (Strict)**: 논문 원문에 없는 자의적인 가상 유즈케이스 목록이나 근거 없는 실무 체크리스트를 임의로 날조하여 추가하지 말 것. 오직 논문이 직접 다룬 시스템 경계(System Boundary), 구현 분석, 실험적 논의에만 철저히 입각하여 서술.
5. **[5. Summary & Actionable Key Takeaways]**:
   - `> [!NOTE] 핵심 요약 (Key Takeaways)` 카드로 바쁜 독자를 위한 1분 스캔 결론 제공. (하단에 중복 References 섹션을 덧붙이지 않고 결론 카드로 힘있게 마무리).

## 🖼️ 3. 이미지 및 썸네일 규격과 우선순위 원칙 (Image Priority & Thumbnails)
- **공식 이미지 최우선 수록 원칙 (중요)**: 
  1. 외부 아티클 및 논문을 인용할 때는 원문 링크에 포함된 **진짜 공식 이미지(실제 보도자료 사진, 논문 원천 도표 및 다이어그램)**를 최우선적으로 검토하고 본문에 수록해야 합니다. cURL 챌린지나 403 에러 등의 웹 장벽을 만나더라도 대체 스크래핑 기술이나 타 매체 인용 소스를 끝까지 추적해 진짜 원본 리소스를 발굴하십시오.
  2. **원문 인라인 SVG / CSS 인터랙티브 다이어그램 전수 조사 및 자동 캡처 의무 (Strict)**: 단순 `.png/.jpg` 확장자 정규식에만 의존하지 마십시오. React, Next.js, Tailwind 등으로 구축된 최신 기술 블로그는 다이어그램을 `<svg>`, `canvas`, `.rounded-xl`, `.border` 등의 DOM 컴포넌트로 렌더링합니다. 원문 분석 시 이러한 시각 요소가 존재하면 사용자가 지적하기 전에 **반드시 헤드리스 브라우저(`google-chrome --headless=new --force-device-scale-factor=2`)로 고해상도 캡처하여 본문 Figure로 100% 수록**하십시오.
  3. 원문 이미지를 누락 없이 우선 매핑한 후에, 여전히 텍스트 배치가 단조롭거나 가독성을 보완할 시각 자료가 더 필요하다고 비판적으로 판단될 때에 한해서만 Notion 2D 테마 등의 개념 그래픽을 AI(`generate_image`)로 보조 생성하여 결합합니다. (이때 AI 이미지에는 '공식' 캡션을 달아 사기 치지 않고 '개념도/예시'임을 명시할 것)
- **공식 이미지 추출 한계 시 우회 전략 (Fallback Extraction Strategy)**:
  1. **웹사이트 이미지 추출 락(Lock) 우회**: 웹 아티클에서 직접적인 이미지 다운로드나 경로 추출이 차단된 경우(복사 방지, Canvas 렌더링 등), 해당 웹페이지를 스크린샷(PNG)으로 캡처하여 PDF로 묶은 뒤 `pdf-layout-extractor` 스킬을 작동시켜 원하는 도표/차트 영역만 정밀 분할 크롭해 기용합니다.
  2. **HTML 부재 시 PDF 추출**: 텍스트 중심의 HTML 원천 소스가 없고 인포그래픽 중심의 파일만 존재하는 경우, 해당 자료를 PDF 파일로 우선 확보하여 `pdf-layout-extractor` 스킬을 가동해 수록 그림들을 무인 자동 추출합니다.
- **원문 메타 정보 상단 일원화 및 하단 중복 제거 규칙 (중요)**:
  - 각 Figure 캡션 뒤에 지저분하게 `(출처: url)` 형식을 덧붙이지 마십시오.
  - **포스팅 최상단에 `> [!NOTE] 원문 논문 메타 정보` 카드**를 배치하여 제목, 저자, 기관, arXiv/원문 링크, 공식 깃허브/사이트 링크를 완결성 있게 일원화 제공하십시오.
  - **하단 중복 References 섹션 작성 금지**: 상단에서 이미 모든 메타 정보와 링크를 제공했으므로, 본문 최하단에 동일한 링크를 단순 나열하는 `## 참고 문헌 및 출처` 섹션은 **100% 중복(Redundancy)이므로 작성하지 않고 결론부 핵심 요약 카드로 글을 깔끔하게 종결**합니다.
  - **면책 조항 기재 금지**: 딱딱하고 방어적인 면책 조항(Disclaimer)이나 정형화된 법적 boilerplate 문구는 기술 블로그 글의 자연스러운 흐름과 신뢰도를 해치므로 **절대로 포스팅 꼬리표나 노트 카드에 포함시키지 마십시오**.
- **논문 PDF Figure 추출 프로토콜 (필수)**:
  1. `pdfimages`는 벡터 그래픽 차트를 추출하지 못합니다. **반드시 `pdftoppm -png -r 200`으로 페이지 전체를 고해상도 렌더링**합니다.
  2. 렌더링된 각 페이지 이미지를 **`view_file`로 직접 눈으로 확인**하여 Figure가 어떤 페이지의 어떤 y 좌표에 위치하는지 파악합니다.
  3. Pillow 등으로 픽셀 좌표를 지정하여 **Figure 영역만 정밀 크롭**합니다. 제목, 저자, 본문 텍스트 등이 포함되지 않도록 합니다.
  4. 크롭 결과물을 **반드시 다시 `view_file`로 확인**합니다. 잘렸거나 불필요한 요소가 포함되면 좌표를 재조정하고 다시 확인합니다.
  5. 확인이 완료된 이미지만 `drafts/` 폴더에 배치합니다. **눈으로 확인하지 않은 이미지는 절대 사용하지 않습니다.**
- **썸네일 공통 규칙**: **글자 삽입 절대 금지 (Strictly No Text, No Labels)**, **15% 모바일 안전 여백**, **추상 이론의 물리적/기하학적 은유화**, **최대 5–7개 핵심 오브젝트 제한 (Max 7 Primary Elements Distill Rule)**.
- **모바일 과밀 방지 규칙 (Max 7 Elements)**: 초소형 화면(<120px) 및 피드 스크롤 시 시각적 노이즈를 방지하기 위해, 썸네일 내 시각 요소(노드, 아이콘, 블록 등)의 개수를 **최대 5–7개 이하로 압축·증류**합니다. 복잡한 방사형 노드 나열을 지양하고 1개의 중심 코어와 3–5개의 주요 브랜치로 단순화합니다.
- **썸네일 본문 삽입 절대 금지 (중요)**: `thumbnail.jpg`는 YAML Front-matter 메타데이터에만 명시하며, **포스트 본문 영역 내부에는 절대로 직접 삽입(Figure 1 등으로 렌더링)하지 말 것**.
- **Notion 테마 (추천)**: 2D 일러스트, 따뜻한 크림 배경(#FAF9F6), 차콜 라인(#1C1917), 1개 포인트 컬러, 최대 5–7개 절제된 시각 오브젝트. (주제: 로봇/사물의 직관적인 상호작용 메타포)
- **Stripe 테마**: 2D 등각 투영(Isometric), 매끄러운 그라데이션, 화이트 배경(#FFFFFF).
- **Linear 테마**: 기술 UI 도구 모크업, 1px 미세 와이어프레임, 다크 모드 슬레이트(#0F172A).

## ⚙️ 4. 빌드 파이프라인 작동 규칙
- **빌드 실행**: `node src/build.js drafts/{YYMMDD}_{Index}/index.md`
- **주요 변환 기능**:
  1. TOC(목차) 및 계층구조(h3에 `↳ `) 자동 생성.
  2. `highlight.js` 기반 코드 구문 강조.
  3. GitHub Callout 인용구(`> [!NOTE] 제목`)를 HSL 테마 박스로 변환.
  4. 구글 드라이브 API 연동을 통해 이미지를 CDN 주소(`https://lh3.googleusercontent.com/d/FILE_ID`)로 자동 치환. (해시 비교 증분 업로드 지원 및 브라우저 캐시 무력화를 위해 URL 끝에 `?v=타임스탬프` 쿼리 필수 탑재)
  5. **티스토리 네이티브 이미지 모아보기 지원 (phocus 뷰어 연동)**:
     - 모든 `<img>` 태그는 티스토리 순정 뷰어가 정상 감지할 수 있도록 아래 HTML 구조로 래핑하여 컴파일해야 합니다.
     ```html
     <figure class="imageblock alignCenter" data-ke-mobileStyle="widthOrigin">
       <span data-url="이미지URL?v=시간" data-phocus="이미지URL?v=시간">
         <img src="이미지URL?v=시간" alt="설명" loading="lazy">
       </span>
       <figcaption>설명</figcaption>
     </figure>
     ```
  6. **모바일 반응형 레이아웃 뷰포트 규격**:
     - 모바일 크롬 브라우저 등에서 티스토리 자체 스킨 패딩과 우리 포스팅 패딩이 겹쳐 본문 영역이 지나치게 좁아지는 현상(이중 패딩)을 제어하기 위해 768px 이하 해상도 미디어 쿼리를 필수로 적용합니다.
     - 모바일 규격: `max-width: 100%`, `padding: 0 8px`, `font-size: 15.5px`.
     - 대화형 이미지 스크롤: 가로폭이 매우 넓은 다이어그램 등은 반응형 축소 시 글씨 뭉개짐을 피하기 위해 `figure.imageblock`에 `overflow-x: auto` 및 `min-width: 680px` (img에 적용) 등의 가로 휠 스크롤 보호 조치를 동반합니다.

## 📂 6. 자가 사후 리뷰 프로세스 (Post-Writing Self-Review) (필수)
원고 작성 완료 및 빌드 전 다음 사항을 스스로 최종 검토합니다:
1. **논리 흐름**: 핵심 설명이 `> [!NOTE]` 박스에 부적절하게 격리되지 않고 정식 문단 및 H3 헤더로 흘러가는가?
2. **밋밋함 방지**: 텍스트 단조로움을 피하기 위해 썸네일, 다이어그램(그리드 카드), 이모지 액센트 등이 시각적으로 배치되었는가?
3. **Git 위생**: `dist/` 및 무거운 `.pdf`, `.mp4` 파일들이 `.gitignore`에 의해 차단되었는가?

## ⚖️ 7. 절대적 지적 정직성 및 정량 검증 원칙 (Strict Intellectual Honesty & Verification)
- **거짓말 및 추측 사실화 금지 (Strictly No Falsehoods)**: 
  - 에이전트는 존재 여부가 확인되지 않은 404 가상 URL을 임의로 날조하여 기재하거나, 검증되지 않은 외부 요약본을 교차 검증 없이 포스팅과 참고 문헌에 꽂아서는 안 됩니다.
  - 자신이 cURL PING이나 직접 접속으로 물리적/내용적 확인을 거치지 않은 리소스에 대해 "완벽히 확인했다"고 사용자에게 허위 보고하는 나태한 기만을 절대 금지합니다.
- **물리적 및 정성적 검증 절차 의무화 (Semantic URL Verification)**:
  - 모든 1차 출처 링크는 기재 전 쉘에서 `curl` 응답 코드를 쏘아 실제 200 OK 페이지가 뜨는지 점검함은 물론, **직접 페이지를 파싱하거나 내용을 조회하여 해당 아티클의 타이틀과 본문이 포스팅 본문 맥락(주제 지식)과 100% 일치하는지 육안/데이터 레벨에서 정성 대조 검증**해야 합니다.
  - 상태 코드가 200 OK라도 엉뚱한 다른 소식(예: 배터리 조정 기사 등)을 다룬 링크인 경우, 해당 링크는 무효 리소스로 판정하고 기재를 즉시 소거해야 합니다. (메인 홈페이지나 도메인 루트 주소로 퉁치지 말 것)
- **수정 후 빌드 구동 및 로그 검토 의무화 (Mandatory Post-Edit Build Run)**:
  - 포스팅 원고 마크다운 파일이나 빌드 관련 코드를 수동으로 단 한 줄이라도 수정했다면, 사용자에게 완료 보고를 하기 전에 **반드시 `node src/build.js drafts/{폴더}/index.md` 명령어를 터미널에서 재구동**해야 합니다.
  - 빌드 시 터미널에 노출되는 모든 **에러(Error)** 및 **경고(Warning)** 로그를 무시하지 말고 꼼꼼히 정독하여, 불완전하거나 비정상 응답(403 등)을 반환하는 링크가 섞여 있는지 눈으로 크로스 체크해야 합니다.
